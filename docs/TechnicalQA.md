# MOA 기술 발표와 질의응답

2026-11-05 `origin/main`의 `c696348` 기준이다. 백엔드 구현을 설명하는 답변이며 AI 서버 내부 알고리즘·운영 배포 상태·성능 수치를 대신 증명하지 않는다. 구조와 세부 흐름은 [기술 설명서](TechnicalOverview.md), 정확한 HTTP 본문은 [API 명세](APISpec.md)를 함께 사용한다.

## 1. 발표 시작 문장

### 30초 설명

> MOA는 고객 상담과 개발팀의 문제 해결을 연결하는 AI 상담 지원 시스템입니다. 고객 문의가 들어오면 원문과 분석 요청을 함께 저장하고, 별도 AI 서비스가 분류·요약·근거 검색·답변 초안을 생성합니다. 백엔드는 그 결과가 최신 문의와 유효한 문서를 기준으로 했는지 검증한 뒤 담당자에게 제공하거나 정책에 맞는 답변만 자동 발송합니다. 같은 오류 문의가 급증하면 그룹과 장애 구간으로 묶고, 검증된 GitHub 저장소에 조사용 Issue를 연결합니다.

### 2분 기술 설명

> 백엔드는 FastAPI와 비동기 SQLAlchemy, PostgreSQL로 구현했습니다. 사용자·기업·문의·대화·분석·답변은 관계형 데이터로 관리하고, AI의 가변적인 결과와 외부 전달 스냅샷은 JSONB로 보존합니다. 첨부 원본은 비공개 S3에 저장합니다.
>
> 가장 중요한 설계는 AI 호출과 업무 데이터의 확정을 구분한 것입니다. 문의 접수 시 원문과 분석 요청을 하나의 DB 트랜잭션으로 저장해 고객에게 먼저 접수 결과를 반환합니다. worker가 저장된 작업을 가져가 AI를 호출하고, callback과 polling은 같은 결과 적용 함수를 사용합니다. 문의 revision과 기준 메시지, 최신 run을 확인하므로 이전 분석이 늦게 도착해도 현재 상담을 덮어쓰지 않습니다.
>
> 답변 발송도 별도 검증 단계입니다. 담당자가 승인할 때 문의·초안·지식 revision을 확인하고, 인용 문서가 현재 검색 가능한 최신 근거인지 재검사합니다. 자동 응대는 기업별로 명시한 정책과 문서 허용 목록, 검수 조건을 통과해야 하며 기본은 비활성화입니다.
>
> 반복 문의는 오류 코드와 검증된 유사 문의 후보를 기준으로 묶습니다. 최근 5분간 같은 그룹에 실제 문의가 8건 이상이면 급증으로 보고, 오류 문의 조건을 만족하면 GitHub Issue 작업을 등록합니다. 외부 응답이 유실되면 무조건 재전송하지 않고 기존 Issue를 marker로 찾아 중복을 줄입니다. 구현의 중심은 AI 결과를 실제 업무에 안전하고 추적 가능하게 반영하는 데 있습니다.

### 설계를 한 문장으로 요약

> AI는 후보와 초안을 만들고, 백엔드는 권한·최신성·근거·발송 조건을 검증해 업무 상태를 확정합니다.

## 2. 서비스와 아키텍처 질문

### Q01. 일반 챗봇과 무엇이 다른가요?

**답변:** 대화 생성뿐 아니라 담당자 승인, 근거 문서 버전, 고객 평가, 반복 문의 그룹, GitHub 조사 요청까지 연결합니다. AI 응답을 바로 노출하는 대신 현재 문의와 근거가 유효한지 확인하는 업무 흐름을 구현한 것이 차이입니다.

**근거:** [결과 적용](../app/services/analysis.py), [답변](../app/services/answers.py), [그룹](../app/services/groups.py).

### Q02. 왜 FastAPI를 사용했나요?

**답변:** 요청·응답 schema와 API 문서를 함께 관리하고, 인증·DB 세션을 의존성으로 분리하기 적합합니다. AI·GitHub·DB 등 I/O가 많은 구조에서 비동기 HTTP와 DB 접근을 연결하기도 편합니다. 비동기를 쓴다고 CPU 연산까지 빨라지는 것은 아니므로 비밀번호 해시는 thread pool, OCR은 별도 프로세스로 처리합니다.

**추가 질문:** “다른 프레임워크보다 빠르다는 측정이 있나요?”에는 벤치마크 우위가 아니라 현재 구조와 개발 방식의 적합성을 설명한다.

### Q03. 왜 PostgreSQL을 선택했나요?

**답변:** 문의·답변·평가의 관계와 무결성뿐 아니라 동시 쓰기와 작업 복구가 중요하기 때문입니다. FK·유일성 제약·행 잠금·`SKIP LOCKED`·advisory lock·JSONB를 실제로 사용합니다. 따라서 단순 저장소 이상의 역할을 합니다.

**근거:** [모델](../app/db/models/), [분석 작업 확보](../app/workers/analysis.py), [그룹 잠금](../app/services/groups.py).

### Q04. 마이크로서비스인가요?

**답변:** 백엔드는 공통 DB와 기능별 모듈을 가진 하나의 애플리케이션입니다. 모델 실행과 RAG는 별도 moa-ai 서비스에 위임합니다. 백엔드 안의 인증·문서·상담을 각각 독립 마이크로서비스로 나눈 것은 아닙니다.

### Q05. 백엔드와 AI 팀의 책임은 어디서 나뉘나요?

**답변:** AI는 분석·검색·초안·검수 결과를 생성합니다. 백엔드는 인증·기업 격리·원문 저장·분석 요청·결과 최신성·발송·그룹 확정·외부 작업 복구를 담당합니다. 모델과 embedding 설정은 AI 서버에서 관리하고, 백엔드는 정해진 HTTP 계약을 검증합니다.

### Q06. 어떤 모델과 vector DB를 사용하나요?

**답변:** 이 저장소의 운영 기록에는 AWS Bedrock의 Claude Haiku 4.5와 Titan Text Embeddings v2, 1024차원 embedding을 EC2 IAM Role로 호출한 기록이 있습니다. 백엔드가 모델 SDK나 vector DB를 직접 운영하는 구조는 아닙니다. vector 저장소·검색 점수 계산·prompt의 정확한 구현은 moa-ai 저장소 기준으로 설명해야 합니다.

**주의:** 백엔드 코드만 보고 별도 AI 서버의 현재 모델 설정이나 검색 알고리즘을 확정해서 말하지 않는다. [운영 기록](LLMOperations.md).

### Q07. 왜 Redis나 Celery 없이 DB로 작업을 관리하나요?

**답변:** 문의 저장과 분석 의도 저장을 같은 트랜잭션으로 묶을 수 있어, 접수는 됐는데 작업이 사라지는 틈을 줄입니다. worker는 DB의 처리 시각·단계·lease를 보고 작업을 가져갑니다. 운영 구성은 단순해지지만 작업량이 커지면 polling과 잠금이 DB 부하가 되므로 이를 측정한 뒤 큐 분리를 검토해야 합니다.

### Q08. router, service, model을 왜 나눴나요?

**답변:** router는 HTTP 계약, service는 업무 규칙과 트랜잭션, model은 저장 구조와 제약을 담당하도록 나눴습니다. 예를 들어 callback과 polling이 같은 service를 사용하므로 HTTP 경로가 달라도 결과 적용 규칙이 달라지지 않습니다. 별도 repository 계층을 일괄 도입하지는 않았고 서비스에서 SQLAlchemy 쿼리를 수행합니다.

## 3. 상담과 AI 처리 질문

### Q09. 문의 한 건이 들어오면 어떤 순서로 처리되나요?

**답변:** 인증·기업·입력을 확인하고 문의, 첫 고객 메시지, 접수 안내, 첨부 연결, 분석 요청을 함께 저장합니다. 고객에게 201을 반환한 뒤 worker가 분석 요청을 처리합니다. 결과가 오면 최신성을 검사하고 분류·초안·검수·자동 응대 판단·그룹을 반영하며, 고객과 담당자는 각자 허용된 조회 응답을 받습니다.

**근거:** [접수](../app/services/inquiries.py), [분석](../app/services/analysis.py).

### Q10. 왜 고객이 AI 완료를 기다리지 않나요?

**답변:** 접수 성공과 외부 AI 생성 성공을 분리하기 위해서입니다. AI가 느리거나 실패해도 고객 문의는 보존되어야 합니다. 접수 응답은 DB 저장 완료를 뜻하고 분석 결과는 이후 조회로 확인합니다. 고정 접수 안내는 LLM 생성이 아닙니다.

### Q11. 대화 순서는 어떻게 보장하나요?

**답변:** 문의 행을 잠근 뒤 `last_message_sequence`를 증가시키고 메시지를 저장합니다. `(inquiry_id, sequence)`에 유일성 제약을 걸고 조회도 이 순번을 사용합니다. 같은 timestamp나 외부 공개 ID의 크기에 의존하지 않습니다.

### Q12. `revision`은 무엇이고 언제 증가하나요?

**답변:** 문의 내용이나 업무 상태가 어떤 버전인지 표시하는 변경번호입니다. 고객 메시지 추가, 수동 분류, 답변 발송, 종료 같은 변경에서 증가하며, 화면의 기대값과 현재 값을 비교해 오래된 요청을 거절합니다. 이탈·읽음 기록은 대화 내용 변경이 아니므로 revision을 증가시키지 않습니다.

### Q13. AI를 호출하는 동안 고객이 새 메시지를 보내면요?

**답변:** 새 메시지가 revision을 바꾸고 최신 분석 요청을 교체합니다. 이전 결과가 도착해도 저장 당시의 문의 revision과 기준 고객 메시지가 현재와 다르면 `ignored_stale`로 처리합니다. 이전 결과를 이력으로 보존할 수는 있지만 현재 상담을 덮어쓰거나 다시 발송하지 않습니다.

### Q14. callback이 유실되면 결과가 사라지나요?

**답변:** 분석 worker가 등록된 `run_id`를 I02로 조회하므로 callback만 의존하지 않습니다. callback과 polling 모두 같은 결과 적용 함수를 쓰고, 동일 run의 결과 hash로 중복을 식별합니다. 서로 다른 최종 내용이 같은 run으로 오면 충돌로 처리합니다.

### Q15. worker가 중간에 죽으면 어떻게 되나요?

**답변:** 분석·문서·GitHub·Issue 작업은 DB에 남고 임시 소유권인 lease가 만료되면 다시 확보할 수 있습니다. 새 worker는 저장된 단계와 payload를 보고 이어서 처리합니다. 이전 worker가 늦게 돌아와도 lease token이 다르면 결과를 적용하지 않습니다. 요약 worker는 별도로 전용 연결의 session advisory lock을 사용하며 프로세스 종료 시 잠금이 풀립니다.

### Q16. 실행 전에 callback이 먼저 오면요?

**답변:** 백엔드에 run이 등록되지 않았다면 `RUN_NOT_REGISTERED`를 반환합니다. 미확인 run의 결과를 임의로 저장하지 않습니다. 등록 후 callback 재전달 또는 polling으로 같은 결과 적용 경로를 사용합니다.

### Q17. `status`, `run_status`, `processing_stage`는 왜 따로 있나요?

**답변:** 상담 업무 상태, AI 실행 상태, 세부 진행 표시가 서로 다른 개념이기 때문입니다. AI가 실패해도 문의가 없어지는 것은 아니고, 답변이 완료되어도 다음 분석 요청의 이력이 있을 수 있습니다. 무효화된 대기 작업은 조회에서 대기로 계속 보이지 않도록 처리합니다.

### Q18. 담당자가 분류를 수정했는데 AI가 덮어쓰지 않나요?

**답변:** 수동 확정 여부와 수정 전후 값·사유·작업자·revision을 저장합니다. AI 결과 적용 시 수동 확정된 분류는 덮어쓰지 않습니다. 그룹이 이미 있으면 변경된 분류 기준에 맞춰 다시 평가합니다.

### Q19. AI 응답 형식이 바뀌면 어떻게 대응하나요?

**답변:** HTTP 성공만 믿지 않고 Pydantic 계약을 검증합니다. 최근 `routing` 추가에서는 허용 구조를 명시하고 기존 callback과 같은 검수 사유로 정규화했습니다. 선택 필드가 없을 때 기존 결과의 지문을 유지하고, polling과 callback에 같은 뜻의 결과가 와도 충돌하지 않게 검증했습니다.

**주의:** 무조건 extra field를 허용하는 방식이 아니다. 현재 `routing` 처리는 팀 설명을 보존하는 호환성 처리이며 자동 팀 배정 기능과 다르다. [계약 호환 테스트](../tests/test_pipeline_routing_compatibility.py).

## 4. RAG와 답변 신뢰성 질문

### Q20. RAG는 어떤 문제를 해결하나요?

**답변:** 서비스 정책·사용 안내·현재 소스처럼 변경 가능한 자료를 검색해 초안의 근거로 사용하도록 합니다. 이 백엔드는 검색 자체보다 어떤 문서 버전이 유효하고 검색 가능한지, 그 근거가 발송 직전에도 유효한지를 관리합니다. RAG가 있다는 사실만으로 정확도가 보장되지는 않습니다.

### Q21. fine-tuning 대신 RAG를 사용한 이유는 무엇인가요?

**답변:** 이 구조에서는 변경된 정책을 버전으로 관리하고, 인용한 근거를 확인하며, 폐기한 자료를 검색에서 제외하는 것이 중요합니다. 그런 요구는 외부 자료와 생성 모델을 분리하는 RAG 흐름에 잘 맞습니다. 이 저장소에 fine-tuning 학습 파이프라인은 없으며, 두 방식의 정확도를 비교 실험한 결과를 주장하지 않습니다.

### Q22. 문서 `version`과 `source_revision`은 무엇이 다른가요?

**답변:** version은 문서 원문 버전입니다. source revision은 같은 버전의 폐기·재검토·재활성화 같은 검색 상태 변경 순서입니다. 텍스트가 같아도 상태 변경은 더 최신이어야 하므로 별도로 관리합니다. `content_hash`는 원문 텍스트가 같은지 확인하는 값입니다.

### Q23. 인덱싱 완료인데 왜 검색 불가일 수 있나요?

**답변:** 인덱싱 작업 완료와 현재 사용 가능한 근거인지는 별개입니다. 문서가 폐기되거나 재검토 상태이거나, 최신 version·revision이 아니거나 AI가 현재 검색 가능함을 확인하지 못하면 `searchable=false`입니다. 상태가 불명확할 때 안전한 자료로 간주하지 않습니다.

### Q24. 새 문서를 등록하다 실패하면 옛 문서를 계속 쓰면 되지 않나요?

**답변:** 새 버전이 필요한 이유가 정책 변경일 수 있어 옛 내용을 자동 복구하면 잘못된 안내를 할 수 있습니다. 그래서 이전 버전 차단과 새 등록을 단계로 나누고 실패를 보존합니다. 운영자는 원인을 해결하고 저장된 작업을 재시도합니다.

### Q25. 두 개의 knowledge revision이 왜 있나요?

**답변:** `backend_knowledge_revision`은 백엔드가 관리하는 기업의 지식 변경번호이고, AI의 `knowledge_revision`은 AI 검색 상태의 변경번호입니다. 관리 주체와 증가 조건이 다르므로 숫자를 직접 비교하지 않습니다. 백엔드에서는 분석 당시 값과 현재 값을 비교하고, 개별 인용 자료의 상태도 I05로 확인합니다.

### Q26. 담당자가 답변을 누르는 순간 문서가 바뀌면요?

**답변:** 문의·초안의 최신성을 확인하고 기업 지식 변경번호와 문서 잠금 순서를 맞춰 검증합니다. 문서 변경번호나 인용 근거가 달라지면 발송을 거절하고 새 분석·확인을 요구합니다. 외부 AI와 분산 트랜잭션을 쓰는 것은 아니므로 백엔드를 우회한 외부 저장소 변경까지 원자적으로 보장하지는 않습니다.

### Q27. 자동 답변은 어떤 경우에 보내나요?

**답변:** 기업별 정책을 명시적으로 켜고, 허용 분류·문서 버전, 낮은 위험 범위, 완전한 초안, 필수 검수 통과, 근거 인용, 현재 문서·검색 상태, 안전한 본문 조건을 모두 만족해야 합니다. 기본은 비활성화이고 `review_only` 분석은 발송하지 않습니다. 높은 긴급도나 오류 코드가 있으면 자동 범위에서 제외합니다.

**근거:** [자동 발송 조건](../app/services/automatic_responses.py), [정책](../app/core/auto_response.py).

### Q28. 추가 질문도 AI가 쓴 그대로 보내나요?

**답변:** 아닙니다. AI가 알려준 누락 항목을 허용된 항목으로 정규화하고 고정 문구로 질문합니다. 질문 횟수와 중복 내용도 제한합니다. 검수되지 않은 AI 질문이 비밀번호나 개인정보를 요청하는 위험을 줄이기 위한 구조입니다.

### Q29. 사람이 승인하면 모든 검증을 우회할 수 있나요?

**답변:** AI 검수가 실패한 초안도 사람이 수정·승인할 수는 있습니다. 그러나 문의·초안·문서의 최신성, 같은 기업의 근거인지 여부는 계속 검사합니다. 사람의 승인을 AI 검수 통과로 바꾸지 않고 원본과 최종 판단을 따로 보존합니다.

### Q30. hallucination이나 prompt injection을 완전히 막았나요?

**답변:** 완전히 막았다고 주장하지 않습니다. 자료의 출처·상태·revision, 구조화된 응답, 검수 항목, 인용·허용 문서, 자동 발송 본문 필터와 담당자 검토를 함께 사용합니다. 이는 위험을 줄이는 여러 제어이며 문장 의미의 진실성이나 모든 공격을 완전하게 증명하는 장치는 아닙니다.

### Q31. 답변 수정률이 낮으면 좋은 답변인가요?

**답변:** 수정률은 원본 초안과 최종 본문의 문자열 차이를 나타냅니다. 정확도·해결률·고객 만족도의 대체 지표는 아닙니다. 별점·해결 여부와 함께 분석할 수 있는 이력은 저장하지만, 현재 우수 답변을 자동 선정하는 기능은 구현하지 않았습니다.

## 5. GitHub와 반복 장애 질문

### Q32. 유사 문의는 AI가 결정한 그룹에 그대로 넣나요?

**답변:** AI의 후보를 백엔드가 재검증합니다. 오류 코드가 있으면 기업 안의 같은 코드 그룹을 우선하고, 코드가 없으면 유사도 0.85 이상, 같은 분류·기업, 실제 문의와 그룹의 일치 등을 확인합니다. 앱 코드와 AI 코드가 충돌하면 그룹 확정을 보류합니다. 0.85는 판단 임계값이지 원인 일치 확률이 아닙니다.

### Q33. 급증은 무엇을 기준으로 판단하나요?

**답변:** 최근 5분에 같은 그룹의 실제 문의가 8건 이상인지 봅니다. 분석 완료 시각이 아니라 문의 수신 시각을 사용하고 데모 seed는 제외합니다. 문의 메시지 8개가 아니라 문의 8건입니다. 모델 성능 평가에서 도출한 최적 임계값이라고 주장하지 않고 현재 구현 정책으로 설명합니다.

### Q34. 같은 장애에 Issue가 계속 생기지 않나요?

**답변:** 그룹과 장애 구간을 구분하고 구간당 하나의 Issue 작업만 허용합니다. 마지막 수신 후 10분간 조용하면 구간을 종료합니다. worker는 자동 생성 직전에도 최근 오류 문의 임계값을 재검사합니다. 별도 시점에 다시 급증한 경우는 새로운 장애 구간으로 처리할 수 있습니다.

### Q35. GitHub Issue 생성 성공 응답이 유실되면요?

**답변:** 전송 의도를 먼저 커밋하고 Issue 본문의 구간 marker를 조회합니다. 이미 생성되어 있으면 그 URL을 사용합니다. POST 결과가 불확실하고 조회로도 확인할 수 없으면 `확인 필요`로 남깁니다. 무조건 같은 POST를 재시도하면 중복 Issue가 생길 수 있기 때문입니다.

**추가 질문:** “정확히 한 번을 보장하나요?”에는 DB의 구간별 유일성과 외부 결과 확인으로 중복을 줄이며, 외부 API까지 exactly-once를 보장하지 않는다고 답한다.

### Q36. GitHub 연동에 왜 App 설치 외에 사용자 인증이 필요한가요?

**답변:** 설치 ID를 안다는 것만으로 그 설치를 사용할 권한이 입증되지는 않기 때문입니다. state·PKCE를 검증하고 실제 GitHub 사용자가 관리할 수 있는 App 설치와 저장소를 확인합니다. 이후 서버가 발급한 installation token도 선택한 저장소 범위로 사용합니다.

### Q37. webhook 순서가 뒤바뀌면 코드를 옛 버전으로 덮어쓰지 않나요?

**답변:** 이벤트의 `after` SHA를 바로 정답으로 사용하지 않고 수집 시점의 현재 HEAD를 읽습니다. 수집은 immutable SHA 기준으로 수행하고, 작업 generation과 lease token이 오래되면 결과를 버립니다. 이전 검색 자료의 차단과 새 자료 등록도 순서대로 처리합니다.

### Q38. 소스 코드나 고객 개인정보가 외부로 나가지 않나요?

**답변:** 보안 레벨 1은 blob 본문을 수집하지 않고, 레벨 2는 선택 경로·확장자·제외 규칙을 적용하고 알려진 비밀 패턴을 마스킹한 뒤 외부 AI에 내부용으로 전달합니다. “외부로 전혀 나가지 않는다”는 구조는 아닙니다. Issue는 고객 원문 대신 문의 ID와 정해진 요약·허용된 환경 정보를 사용하며 모든 비밀 탐지를 보장하지는 않습니다.

### Q39. 코드가 바뀌면 정책 문서를 자동 수정하나요?

**답변:** 변경 경로에 연결된 문서를 재검토 상태로 만들고 검색·발송 근거에서 차단합니다. 코드 변경을 정책의 정답으로 자동 확정하지 않습니다. 담당자가 내용과 정책을 확인해 새 문서 버전이나 상태를 결정해야 합니다.

### Q40. 오류의 원인 코드를 자동으로 찾고 수정하나요?

**답변:** 현재 구현은 AI 결과가 제안한 코드 경로·SHA가 실제 유효한 GitHub 수집 자료와 일치하는지 확인하고 조사 후보로 연결합니다. 후보가 근본 원인이라는 보장은 없고, 자동 코드 수정·PR 생성·서비스 배포 기능은 아닙니다.

## 6. 보안·사용자 상태·운영 질문

### Q41. 다른 회사 데이터를 조회하지 못하게 어떻게 막나요?

**답변:** JWT 검증 후 DB의 현재 사용자·역할·기업 소속을 읽고 쿼리에서 기업 범위를 제한합니다. 고객 문의는 소유 고객까지 확인합니다. 외부 AI 호출도 서비스 token과 tenant를 전달하고, 결과의 tenant·문의·run을 다시 대조합니다. cursor 서명과 ID 형식만으로 권한을 판단하지 않습니다.

**한계:** 현재 가입 시 역할 선택과 기업 ID 연결을 허용하므로 운영 조직의 초대·승격 검증까지 구현했다고 말하면 안 된다.

### Q42. refresh token이 탈취되거나 동시에 사용되면요?

**답변:** DB에는 원문 대신 hash를 저장하고, 갱신 시 행 잠금 아래 기존 token을 삭제하고 새 token 쌍을 발급합니다. 동시 갱신은 하나만 성공하며 기존 token 재사용은 실패합니다. 이 구현은 token family 전체를 추적하는 재사용 탐지·강제 로그아웃 체계까지 제공하는 것은 아닙니다.

### Q43. 첨부 URL을 알면 누구나 볼 수 있나요?

**답변:** URL 발급 전에는 기업·소유권·연결 상태를 검사합니다. 발급된 presigned URL은 유효기간 동안 접근 권한을 가진 임시 주소이므로 공유되면 그 기간에는 사용할 수 있습니다. 기본 만료는 300초이며 URL을 로그나 영구 공개 링크로 저장하지 않는 연동이 필요합니다.

### Q44. 고객이 창을 닫으면 상담 종료로 바꾸나요?

**답변:** 이탈과 업무 종료를 분리합니다. 이탈은 별도 이벤트와 presence로 기록하고 상담 상태·revision·AI 분석을 변경하지 않습니다. 복귀는 `returned`로 기록합니다. keepalive는 전달 가능성을 높이는 프론트 호출 방식이지 정확한 온라인 상태를 보장하는 연결 프로토콜이 아닙니다.

### Q45. 읽음 위치가 네트워크 역순으로 뒤로 갈 수 있나요?

**답변:** 같은 문의의 메시지인지 검사한 뒤 내부 sequence를 비교해 더 뒤의 위치만 저장합니다. 중복이나 과거 요청은 현재 위치를 반환합니다. 담당자 채팅 읽음은 여러 담당자가 공유하지만 알림 읽음은 사용자별로 관리합니다. GET 조회 자체로 읽음 처리하지는 않습니다.

### Q46. 왜 WebSocket 대신 polling인가요?

**답변:** 현재 구현은 cursor·`has_more`·빈 응답의 위치 보존으로 재조회 흐름을 단순하게 관리합니다. 프론트 계약은 3초 polling이며 연결이 끊겨도 마지막 cursor부터 복구할 수 있습니다. 사용자 수가 커지면 polling 부하와 전달 지연을 측정해 SSE·WebSocket을 검토할 수 있지만 현재 구현된 기능으로 소개하지 않습니다.

### Q47. 테스트는 얼마나 했고 CI에서 무엇을 검사하나요?

**답변:** 현재 코드에서 테스트 711개가 수집됩니다. 실제 PostgreSQL의 테스트별 schema에 migration을 실행하고 인증·권한·동시성·실패·복구를 검증하도록 작성되어 있습니다. AI·GitHub는 HTTP 대역을 사용하며 실제 연동 검증과 구분합니다. 이번 문서 작업은 수집만 확인했고, 현재 GitHub Actions는 의존성 설치와 app import를 검사하며 전체 pytest 단계는 없습니다.

**주의:** “711개가 이번에 모두 통과했다” 또는 “전체 테스트가 CI에서 항상 돈다”라고 말하지 않는다.

### Q48. 배포 실패나 DB migration 충돌은 어떻게 다루나요?

**답변:** 배포는 설정 검증과 migration 성공 후 서비스 재시작으로 진행합니다. 이미 배포된 migration을 바꾸지 않고 merge revision으로 여러 분기를 합칩니다. DB 변경이 성공한 뒤 서비스 재시작이 실패했다고 DB까지 자동 rollback하지는 않습니다. 롤백할 분기와 보존할 데이터를 명확히 하고 검증해야 합니다.

### Q49. 현재 서비스가 정상이라고 무엇으로 판단하나요?

**답변:** `/health`나 배포의 `/docs` 응답은 앱이 응답한다는 신호입니다. DB·S3·AI·worker 전체 정상 상태의 보장은 아닙니다. AI 점검 스크립트는 설정·HTTP 인증을 확인하고, 실제 생성은 테스트 문의가 분석·초안·고객 공개 흐름까지 이어지는지 별도로 확인해야 합니다.

### Q50. 가장 어려운 기술 문제는 무엇이었나요?

**답변 예시:** 외부 AI와 GitHub의 처리 시점이 DB 트랜잭션과 다르다는 점입니다. 접수 직후 프로세스가 죽거나, AI 결과보다 새 메시지가 먼저 오거나, Issue 생성 응답이 유실되는 상황을 구분해야 했습니다. 이를 해결하기 위해 작업 의도를 영속 저장하고 revision·lease token·멱등키·결과 hash·Issue marker를 목적에 맞게 사용했습니다.

**말할 때:** 실제 본인이 담당한 구현과 확인한 사례를 골라 설명한다. 모든 모듈을 혼자 설계하거나 운영 장애를 직접 경험했다고 덧붙이지 않는다.

### Q51. 처리 성능·AI 정확도·운영 비용은 어느 정도인가요?

**답변:** 이 저장소의 코드와 기능 테스트만으로 p95 지연·동시 사용자 수·답변 정확도·건당 비용을 확정할 수는 없습니다. timeout이나 재시도 한도는 성능 측정치가 아닙니다. 정확도는 별도 라벨 데이터와 평가 지표, 지연은 접수와 AI 완료를 구분한 부하 테스트, 비용은 실제 모델·embedding 호출량으로 측정해야 합니다.

### Q52. 다음 개선 우선순위는 무엇인가요?

**답변:** 현재 구현을 운영 규모로 확장한다면 먼저 조직 가입·관리자 권한 부여 정책과 CI의 DB 통합 테스트를 보완하겠습니다. 이후 DB·외부 서비스 readiness, worker 대기시간·재시도·잠금 경합 지표, 고아 파일·만료 데이터 정리, 공개 ID 한도를 다루겠습니다. 모델 정확도 개선과 별개로 운영 실패를 발견하고 복구할 수 있어야 하기 때문입니다.

## 7. 데모 설명 순서

실제 동작을 시연하려면 대상 기업, AI 허용 tenant, API·분석·문서·GitHub·그룹 worker 설정과 필요한 문서·App 설치를 미리 확인한다. 운영 데이터에 반복 테스트하지 말고 시연용 데이터를 구분한다.

| 순서 | 화면·행동 | 말할 내용 | 확인할 결과 |
|---|---|---|---|
| 1 | 고객 문의 접수 | “먼저 원문과 처리 의도를 보존합니다.” | 문의 ID와 접수 안내 |
| 2 | 담당자 상세 조회 | “AI 분석 상태와 상담 상태는 별개입니다.” | run 상태·분류·요약·초안 또는 추가 질문 필요 |
| 3 | 문서 근거·검수 확인 | “생성 결과뿐 아니라 근거 버전과 검수도 확인합니다.” | 유효 근거·검수·검토 사유 |
| 4 | 담당자 답변 승인 | “현재 문의·지식 revision을 검증한 뒤 발송합니다.” | 고객 채팅의 최종 답변·answer ID |
| 5 | 고객 읽음·이탈·복귀 | “읽음과 이탈은 업무 상태를 바꾸지 않습니다.” | 담당자 presence·읽음, 기존 상태 유지 |
| 6 | 상담 종료·평가 | “종료와 해결 확인은 고객 평가로 구분합니다.” | closed 상태·별점·해결 여부 |
| 7 | 시연용 실제 접수로 동일 오류 급증 | “5분간 8건과 실제 수신 시각을 사용합니다.” | 그룹·급증 알림·episode |
| 8 | GitHub Issue 확인 | “코드 후보를 조사 요청으로 연결합니다.” | 검증된 대상 저장소의 Issue와 marker 기반 중복 방지 |
| 9 | 연결된 정책 경로 변경 | “코드 변경을 정책의 정답으로 간주하지 않습니다.” | 연결 문서 재검토·검색 차단·새 source 동기화 |

자동 답변 정책이 꺼져 있다면 3~4단계는 담당자 승인 경로로 시연한다. 문서 근거가 없어 추가 질문이 필요한 결과는 처리 오류와 구분한다. AI·GitHub 준비가 안 된 경우 실제 성공처럼 보이는 mock 화면이나 임의 진행률로 대체하지 말고 저장된 작업 상태와 필요한 설정을 설명한다.

## 8. 마지막으로 기억할 숫자와 용어

| 항목 | 현재 코드 기준 |
|---|---|
| API | 36개 경로, 38개 HTTP 동작 |
| 업무 테이블 | 31개; `alembic_version` 제외 |
| 테스트 | 711개 수집; 이 문서 작업에서 전체 실행 아님 |
| 대화 polling | 프론트 계약상 3초 |
| 급증 / 조용한 구간 종료 | 5분 8건 / 마지막 수신 후 10분 |
| 코드 없는 유사 문의 후보 | 점수 0.85 이상과 추가 범위 검사 |
| access / refresh 기본 만료 | 1시간 / 7일 |
| 첨부 / PDF | 10MiB / 20페이지 |
| 다운로드 URL 기본 만료 | 300초 |
| 분석 worker lease / 전체 deadline | 60초 / 10분 |
| 문서·GitHub worker lease | 600초 |
| idempotency | 같은 업무의 중복 실행 방지 |
| revision | 현재 업무·소스의 변경 기준 |
| lease token | 지금 작업을 소유한 worker 확인 |
| barrier | 과거 검색 자료가 사용되지 않도록 차단 확인 |
| reconcile | 외부 처리 결과를 조회해 실제 상태와 맞추는 단계 |
| fail closed | 유효성을 확인하지 못한 자료·발송을 허용하지 않는 처리 |

핵심 단어를 나열하는 대신 “어떤 실패를 막기 위해 어느 시점에 사용했는가”를 사례와 함께 설명한다.
